# `data/hm-intel/<slug>.json` schema

Personal hiring-manager intelligence files generated by
`scripts/hiring-manager-research.mjs` (multi-LLM, ~$5-30/run per role) and
consumed by:

- `lib/hm-match-check.mjs` (pre-apply-check HM-match sub-check)
- `scripts/agents/hm-chance.mjs` (HM-chance drawer popout)
- `scripts/agents/interview-likelihood.mjs` (Interview-likelihood drawer popout)
- `lib/ground-prompt.mjs` (RAG context for drawer popouts)

Files are gitignored (personal data). The exceptions explicitly UN-ignored
by `.gitignore`:

- `_weights.json` — scoring weights, see file for tunables
- `_schema.md` — this document

## File naming

`data/hm-intel/<slug>.json` where `<slug>` = `<company-slug>-<role-slug>`,
both kebab-cased. Examples:

- `anthropic-applied-ai-architect-industries.json`
- `ema-solutions-architect.json`
- `openai-ai-deployment-engineer-media-partnerships.json`

The apply-pack slug (e.g. `048-anthropic-aaa-industries`) is NOT identical
to the hm-intel slug. `loadHmIntel()` in `lib/hm-match-check.mjs` strips
any leading numeric prefix and tries both forms.

## Top-level fields

| Field | Type | Required | Notes |
|---|---|---|---|
| `company` | string | yes | Short company name (e.g. "Anthropic") |
| `role` | string | yes | Job title (e.g. "Applied AI Architect, Industries") |
| `url` | string | no | Source URL (often a LinkedIn jobs URL — may expire) |
| `synthesized_at` | ISO8601 string | yes | Generation timestamp |
| `providers_called` | string[] | yes | Model identifiers attempted (e.g. `anthropic:claude-sonnet-4-6`) |
| `providers_succeeded` | string[] | yes | Model identifiers that returned content |
| `role_summary` | string | yes | One-paragraph role context |
| `alignment_with_goals` | string | yes | One-paragraph fit narrative for Mitchell |
| `fit_evidence` | object | yes | Sub-keys: `career_history`, `skills_match`, `narrative_arc` (each string) |
| `hiring_managers` | object[] | yes | `{name, title, linkedin_url?, why_owns_this_req?}` per HM |
| `recruiters` | object[] | yes | `{name, title, linkedin_url?, professional_email?, professional_email_source?}` |
| `comp_intelligence` | object | yes | `{base_range, equity_summary, total_comp_estimate, comp_sources[]}` |
| `outreach_strategy` | object | yes | `{best_first_move, lead_with}` (each string) |
| `signals` | string[] | yes (post-migration) | 5–15 capability-shaped HM signals — see below |
| `_meta` | object | no | `{owner, method, cost_usd, providers_succeeded_count}` |

## The `signals[]` field (added 2026-05-25)

`signals[]` is the load-bearing field for `lib/hm-match-check.mjs`'s
scoring rubric. It's a list of 5–15 short strings describing what the
hiring manager filters for in a candidate. The HM-match score rolls up
how many `signals[]` entries the applicant's artifacts (CV + cover letter)
demonstrate vs leave as gaps.

### Constraints

- **Length**: 5–15 entries
- **Per-entry length**: ≤ 12 words (≤ 200 chars hard cap)
- **Shape**: Capability- or team-shape descriptors. **NOT PII** —
  no names, emails, phone numbers, URLs
- **Source**: Drawn directly from `role_summary` + `alignment_with_goals` +
  `fit_evidence` + `outreach_strategy`. Don't invent signals not present
  in the intel
- **Distinctness**: No near-duplicates (case-insensitive)
- **Example shapes**:
  - "ships production agent systems"
  - "bridges customer-facing solutioning + technical depth"
  - "fluent in vertical-specific workflow context"
  - "translates technical capability into business outcomes"

### Validation

`scripts/migrate-hm-intel-add-signals.mjs` enforces all the constraints
above via `validateSignals()`. PII patterns checked include:

- email regex (`@` + domain)
- URL regex (`http://`, `https://`, `www.`)
- phone-shaped digit clusters (US + international)

A malformed signals[] response from the migration model ABORTS the run
without modifying any files.

## Migration history

| Date | Change | Script |
|---|---|---|
| 2026-05-25 | Added `signals[]` field | `scripts/migrate-hm-intel-add-signals.mjs` |

To re-derive `signals[]` for a file (e.g. after editing role_summary):
delete the existing `signals[]` field and re-run the migration on that
slug. The script is idempotent — files that already have a non-empty
`signals[]` are skipped.

## Backward compatibility

`lib/hm-match-check.mjs::buildPersonaBlock()` accepts files with OR without
`signals[]`. When the field is absent, the persona block falls back to
deriving signals from the unstructured prose fields — the model does the
extraction in-flight. Quality is lower but the path still works.

After migration completes, every hm-intel file has a stable `signals[]`
field — the LLM can score against an explicit checklist, signals match
counts are deterministic, and the `gaps[]` orchestrator surface becomes
load-bearing.
